# OASIS 技術スタック

- 文書ステータス: Proposal
- 対象: macOS版MVP
- 最終更新日: 2026-09-19

## 1. 方針

OASISは、端末内推論と利用者によるデータ管理を中核に置く。MVPでは、macOSとの統合品質、配布の単純さ、推論ランタイムの交換可能性を優先する。

技術選定の優先順位は次のとおり。

1. プライバシーとローカル実行
2. macOSネイティブの操作感と省電力性
3. 障害分離とデータの回復性
4. モデル・入力方法・ツールの交換可能性
5. 開発と配布の再現性

## 3. アーキテクチャ

```text
┌────────────────────────────────────────────┐
│ macOS App                                  │
│  SwiftUI / AppKit / Menu Bar / Shortcut    │
├────────────────────────────────────────────┤
│ Application                                │
│  Conversation / Memory / Context / Settings│
├───────────────┬───────────────┬────────────┤
│ Inference API │ Storage API   │ Tool API   │
├───────────────┼───────────────┼────────────┤
│ llama.cpp     │ SQLite/FTS5   │ OS adapters│
│ embedding     │ Keychain      │ permissions│
└───────────────┴───────────────┴────────────┘
```

依存方向はUIからアプリケーション層、アプリケーション層から抽象インターフェースへ向ける。推論、保存、OS連携の実装詳細をUIへ漏らさない。

## 4. モジュール構成案

```text
OASISApp
├── AppUI              # SwiftUI画面、状態ビジュアル、メニューバー
├── AppCore            # ユースケース、ドメインモデル、ポリシー
├── InferenceKit       # LLM/埋め込みの抽象化と実装
├── MemoryKit          # 会話、メモ、検索、コンテキスト構築
├── ContextKit         # 選択テキスト、共有入力、文書取り込み
├── ToolKit            # 許可、確認、実行、監査ログ
├── StorageKit         # SQLite、マイグレーション、Keychain
└── Observability      # OSLog、性能指標、診断情報
```

### 4.1 境界となる主要インターフェース

- `InferenceEngine`: モデルのロード、生成、ストリーミング、キャンセル
- `EmbeddingEngine`: テキストのベクトル化
- `ConversationRepository`: 会話とメッセージの永続化
- `MemoryRepository`: メモの保存、検索、削除
- `ContextProvider`: 利用者が許可したコンテキストの取得
- `ToolExecutor`: 実行前確認、実行、結果、監査情報

これらをプロトコルとして定義し、テスト用実装と将来の別ランタイムを差し替え可能にする。

## 5. クライアントアプリ

### 5.1 Swift / SwiftUI

- macOS固有API、アクセシビリティ、Keychain、メニューバーとの統合を優先し、Swiftを採用する。
- 主要画面はSwiftUIで実装する。
- グローバルショートカット、ウィンドウ制御、テキスト連携などSwiftUIだけで不足する箇所にAppKitを限定利用する。
- UI状態は単一方向データフローを基本とし、推論ストリームとキャンセルをSwift Concurrencyで扱う。

### 5.2 状態ビジュアル

- 初期実装はSwiftUIの`Canvas`またはMetalシェーダーを候補とする。
- MVPでは、見た目よりも低CPU/GPU使用率、状態判別、Reduce Motion対応を優先する。
- Metal採用はプロファイル結果を見て判断し、初期段階から必須にしない。

## 6. ローカル推論

### 6.1 LLMランタイム

第一候補はllama.cppとGGUFモデルの組み合わせとする。

採用理由:

- Apple Siliconを含むローカル実行の実績
- 複数量子化モデルを選択できる
- Metalによる高速化を利用できる
- ランタイムをアプリに組み込む選択肢と別プロセスに分離する選択肢がある

初期の技術スパイクでは、次を比較する。

- アプリ内ライブラリとしての組み込み
- XPCサービスまたは子プロセスとしての分離
- MLX系ランタイム

クラッシュ分離、キャンセル、メモリ解放、署名・配布の容易さを評価し、最終方式を決める。UIは`InferenceEngine`にのみ依存させる。

### 6.2 モデル管理

- モデル本体はApplication Support配下の専用ディレクトリに保存する。
- ダウンロード後にSHA-256を検証する。
- モデルごとに配布元、バージョン、容量、推奨メモリ、ライセンスを記録する。
- リポジトリへモデル本体をコミットしない。
- 初期モデルは、品質、メモリ使用量、日本語性能、再配布条件をベンチマークして決定する。

### 6.3 ストリーミングとキャンセル

- トークン生成は`AsyncSequence`相当のインターフェースでUIへ渡す。
- 利用者の停止操作、画面破棄、モデル切替時にキャンセルを伝播する。
- 推論キューは同時実行数を制限し、メモリ競合を避ける。

## 7. 記憶と検索

### 7.1 SQLite

- 会話、メッセージ、メモ、タグ、モデル情報、設定メタデータをSQLiteに保存する。
- 全文検索にはFTS5を利用する。
- スキーマ変更は順序付きマイグレーションで管理する。
- 書き込みはトランザクション化し、WALモードの適否を検証する。

### 7.2 検索戦略

MVPは、まずFTS5による明示的で説明可能な検索を成立させる。意味検索は次の段階で追加する。

1. キーワード検索で候補を絞る
2. 必要に応じローカル埋め込みで再順位付けする
3. 応答へ使用したメモの識別子を保持し、UIで参照元を表示する

ベクトル保存方式は、SQLiteとの運用一体性、macOS配布、ライセンス、検索性能を比較して決定する。

### 7.3 データ保護

- APIキーなどの秘密情報はKeychainへ保存する。
- 会話DBはユーザー固有のApplication Support配下へ置く。
- File Protection、追加暗号化、バックアップ除外の必要性を脅威モデルに基づいて決定する。
- ログにプロンプト、会話本文、メモ本文を既定で含めない。

## 8. コンテキスト取得とOS連携

- クリップボード利用は、利用者が実行した貼り付けまたは取り込み操作に限定する。
- 選択テキスト取得は、macOS Accessibility API、Services、Share Extensionの候補を技術検証する。
- 権限要求前に、取得対象と目的を説明する。
- 取得内容は確認画面を経てから会話へ追加する。
- 外部コンテンツ内の命令文は信頼せず、プロンプトインジェクション対策境界を設ける。

## 9. 音声

音声をMVPに含める場合の候補は次のとおり。

- 入力: AVFoundationで明示的に録音し、whisper.cppで端末内文字起こし
- 出力: AVSpeechSynthesizer
- 音声セッション: 録音開始・停止と状態表示を同期

常時録音やバックグラウンドでの無表示録音は行わない。音声モデルの容量、遅延、日本語精度を満たせない場合、音声はMVP後へ送る。

## 10. ツール実行と安全性

MVPのツール実行機能は限定的にする。

- `plan`: 実行予定、対象、影響を構造化する
- `authorize`: 利用者へ確認し、今回のみ・継続許可などの範囲を記録する
- `execute`: 許可されたアダプターだけを実行する
- `audit`: 実行日時、対象、結果を保存する。ただし機密本文は保存しない

外部テキストをツール引数へ直接渡さず、型と許可範囲を検証する。破壊的操作や外部送信は個別確認を必須とする。

## 11. ログ・診断・計測

- 構造化ログにはOSLogを使用する。
- ログレベルとプライバシー指定を設定し、利用者コンテンツを秘匿する。
- ローカルで次の指標を確認可能にする。
  - アプリ起動時間
  - モデルロード時間
  - 最初のトークンまでの時間
  - 生成トークン毎秒
  - ピークメモリ
  - 検索時間
- 外部テレメトリはMVPでは既定無効とする。

## 12. テスト戦略

### 12.1 自動テスト

- Swift Testing: ドメインロジック、コンテキスト構築、権限ポリシー、マイグレーション
- XCTest / XCUITest: 起動、会話、停止、履歴削除、権限拒否時の動作
- 契約テスト: `InferenceEngine`、Repository、Toolの各実装
- スナップショットまたは画像比較: 状態ビジュアルと主要画面（導入は必要性を確認）

### 12.2 性能・品質評価

- 対象Macごとのモデルロード時間、生成速度、ピークメモリ
- 日本語の要約、指示追従、長文処理の固定評価セット
- オフライン動作と意図しない通信の検査
- DB異常終了、ディスクフル、モデル破損からの回復試験

## 13. CI/CD

GitHub Actionsで次を実行する。

1. SwiftFormatまたはSwiftLint（採否は初期セットアップ時に決定）
2. ビルド
3. 単体テスト
4. 依存関係とライセンスの検査
5. リリース候補の署名・notarization

署名証明書やnotarization認証情報はGitHub Secretsで管理する。フォークからのPRでは秘密情報を使用するジョブを実行しない。

## 14. 配布

初期候補は、Developer IDで署名・notarizeしたアプリの直接配布とする。自動更新を導入する場合はSparkleを候補とし、更新署名と配布経路を検証する。

Mac App Store配布は、サンドボックス、モデル容量、実行方式、Accessibility API利用との適合性を調査した後に判断する。

## 16. 初期技術スパイク

実装開始前に、次を小さな検証アプリで確認する。

1. 候補モデルの日本語品質、TTFT、生成速度、ピークメモリ
2. llama.cppの組み込み方式とプロセス分離方式の比較
3. ストリーミング、停止、モデル切替後のメモリ解放
4. FTS5検索とローカル埋め込み検索の品質・速度比較
5. グローバルショートカットと選択テキスト取得に必要な権限
6. 署名・notarization済みアプリでの推論ランタイム動作
7. 状態ビジュアルのCPU/GPU負荷とReduce Motion対応

スパイク結果をADRへ記録し、「第一候補」の項目を採用または却下する。

## 17. 保留事項

- 対応macOS最低バージョンとSwift/Xcodeバージョン
- 初期モデルと推奨ハードウェア別の量子化設定
- 推論ランタイムのアプリ内組み込みかプロセス分離か
- 埋め込みモデルとベクトル保存方式
- 音声機能のMVP採用可否
- サンドボックスと配布チャネル
- 外部AIサービスを任意で追加する場合の秘密情報・同意モデル
